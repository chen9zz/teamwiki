# TeamWiki v0.3 design

The user authorized the recommended v0.3 scope and its implementation, testing, fixes and GitHub synchronization. Keep the modular monolith, tenant boundaries, CAS saves and transactional Outbox.

## ZIP hierarchy
- Preserve relative Markdown paths by creating an editable, empty page for each nonempty directory, then create each Markdown document under its directory page. A directory and a document with the same displayed title remain distinct stable IDs; do not merge with preexisting workspace pages.
- Directory identity is scoped to one ImportJob using a reserved `dir:` item key; document keys remain their validated relative paths. Retries and duplicate delivery create each directory/document/revision once, in the existing atomic transaction.
- `total`, `processed` and `result` continue to count/return Markdown documents, not synthetic directories. Progress remains atomic, not live per-file progress.
- Maintain all upload/expanded/file/count/ratio limits. Additionally bound directory count and depth, and reject unsafe or ambiguous directory paths. Proposed bounds: 200 generated directories, 20 directory levels, 400 total pages including up to 200 documents. Empty directories do not create pages.

## Frontend pagination
- Use bounded metadata queries for the document tree and load children on expansion; paginate sibling collections with an explicit load-more action. Never treat an unloaded ancestor as a root or require loading every document body.
- Preserve existing document API compatibility; any new tree/summary endpoint rechecks membership, validates parent scope, has deterministic ordering and limits. Keep existing mutation invalidation coherent so create/move/delete/import updates the tree.
- Page history loads bounded batches and offers load-more for older revisions; workspace/page changes reset pagination. Opening a direct document URL still works when its ancestors are not loaded.
- Parent selectors must preserve the current parent even if it is outside loaded batches; prevent silent reparenting due to incomplete data. Search/home views must not imply a partial collection is the complete workspace.

## Real browser E2E
- Add Playwright Chromium against the built app, real API, PostgreSQL, Redis and Celery/Beat, without API response stubs. Use one CI worker and test-owned accounts/workspaces, leaving demo data intact.
- Cover login/editor/save, two independent browser contexts producing 409 with draft retained, Viewer refusal, nested ZIP import completion/tree display, and document/history pagination across batch boundaries.
- Retain unit/API and production DOM tests. CI container job runs the browser suite with failure traces/screenshots and diagnostic logs.

## Verification and release
- Reproduce missing hierarchy/pagination behavior with targeted tests before implementation. Run full PostgreSQL/Redis backend suite, frontend tests/typecheck/production regression, migrations and real built-app browser E2E.
- Use an isolated checkout and isolated database/container stack. Do not overwrite the existing demonstration database. Record actual results and limitations, update version/OpenAPI/docs, review independently, publish to the existing public GitHub repository, and verify remote CI.
- Public artifacts must omit credentials, personal absolute paths, runtime volumes and browser auth state. No new production-service dependencies beyond Playwright development tooling.
