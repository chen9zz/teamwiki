# 并发方案与可重复验证

## 推荐方案

保留 FastAPI 模块化单体，以 PostgreSQL 作为页面、权限、版本和历史的唯一权威；API 使用两个进程，后台导入保留 Celery。先消除同一空间中无关页面互相等待、重复全空间链接索引和重复 Redis 建连，再按实测调整资源。当前没有引入微服务、数据库分片或额外搜索集群的依据。

| 方案 | 收益与代价 | 选择依据 |
| --- | --- | --- |
| 两个 API 进程 + 有界连接池 + PostgreSQL 行锁/CAS | 复用现有事务和权限模型，部署与排错简单；仍受单个 PostgreSQL 和单机容量约束 | 本次采用，适合作为团队知识库的起点 |
| 更多 API 副本，必要时增加 PgBouncer | 可以扩展无状态入口，但连接预算随进程数相乘；需要独立负载均衡和可观测性 | 当持续测量显示 API CPU 或连接数量成为瓶颈时再评估 |
| 将导入等慢任务放入队列 | 避免长任务占用交互请求；需要幂等、重试和作业状态 | 继续使用已有 Celery/outbox；普通页面保存仍同步提交 |
| 微服务、分片、专用搜索集群、CRDT 协同编辑 | 能满足特定规模或产品需求，同时引入跨服务一致性和运维成本 | 当前基准未证明需要；实时共同编辑属于另一项产品能力 |

两个进程不是高可用方案；单机、数据库和代理仍存在单点。增加副本前先计算所有 API、Celery、迁移和管理连接的总预算。SQLAlchemy 的单进程上限是 `pool_size + max_overflow`，因此不能只看单个池的设置。[SQLAlchemy 连接池文档](https://docs.sqlalchemy.org/en/20/core/pooling.html)

## 写入边界

普通正文/标签保存以及值未改变的标题，取得空间行 `FOR SHARE`，再按页面 ID、空间 ID、客户端版本做 CAS 更新。不同页面可以并发保存，同一页面的同一旧版本只允许一个成功。页面快照、审计和链接更新仍在同一事务提交。普通保存只更新该来源页面的链接，保留已经绑定的目标 ID。

新增页面、实际重命名、树结构调整、删除、恢复和成员权限变更继续取得空间行 `FOR UPDATE`，与普通保存互斥，保护链接解析、树检查和权限变更的顺序。这里使用 `FOR SHARE`，因为它与 `FOR UPDATE` 冲突且彼此兼容；不以只保护键值的锁代替它。[PostgreSQL 17 行锁冲突矩阵](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS)

Redis 缓存通过有界池复用连接，失败时页面读取回退 PostgreSQL。缓存与任务 broker 使用独立 Redis 实例：缓存可淘汰，broker 使用持久化与 `noeviction`。仅使用不同逻辑 DB 不会隔离同一实例的内存淘汰策略。[Redis 淘汰策略文档](https://redis.io/docs/latest/develop/reference/eviction/)

Compose 的默认 API 连接预算为 `2 × (5 + 5) = 20`；PostgreSQL 上限为 80，需另留后台任务和管理余量。这是配置预算，不能据此推导能支持多少活跃用户。API 还设置连接、语句与锁等待期限，以及每进程在途请求上限。代理仅对登录/注册设置独立速率限制；普通业务请求由应用在途上限和数据库池做有界保护。这些限制抑制异常突发，不能代替容量规划。[Nginx 请求限速文档](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html)

## v0.4 的读取、检索与批量工作边界

| 压力来源 | 已落地处理 | 实际边界 |
| --- | --- | --- |
| 热点页面读取 | 权限、当前版本和删除状态先查 PostgreSQL，再读含空间/页面/版本的 Redis key；同进程按 key 合并回填、二次检查，TTL 300 秒加 0–30 秒抖动，缓存失败回源 | 缓存命中仍访问数据库；回填合并只在单进程内，不是跨副本分布式锁；新搜索覆盖标记从数据库覆盖旧缓存值 |
| 大量普通保存 | 共享空间锁允许不同页面写入；页面 CAS 拒绝旧版本，修订/审计/链接/分词同事务提交 | 普通保存仍读取空间页面身份/标题元数据；结构变更和批量导入仍排他锁定空间，可能阻塞其他写入 |
| 中文检索 | 工作线程内执行固定 jieba 分词；中文向量 GIN、标题加权，成员与空间过滤及分页；正文前 32,768 字符和每字段 8,192 词元/96 KiB 输出预算 | 词元检索，不是语义或任意子串检索；超长词元使文档覆盖标记为不足，查询丢词则 422；大英文向量超出 PostgreSQL 表示上限返回 413 并回滚 |
| 导航和历史 | 树节点只读取元数据，默认每批 50 行；父页子文档、搜索、历史按批加载 | offset 分页不是并发结构变更下的一致快照；图谱及部分关系查询仍受空间规模影响 |
| 批量导入 | 校验后的 Job 与 Outbox 同事务；Celery 移出交互请求，晚确认、低预取和数据库幂等防重复，滞留任务可恢复 | 队列保证的是可恢复的至少一次投递；整批原子导入仍持有空间排他锁，进度从 0 到 N，不代表每页单独提交 |
| ZIP 导出 | 独立 `REPEATABLE READ READ ONLY` 快照重验权限，预检页数/字节/关系规模，再读取数据；释放快照后在线程压缩；每进程最多 2 个导出，满载返回 503 | 仍是有界同步下载，不是 Celery 导出；快照与请求认证使用有界连接池，线程压缩也有 CPU/内存成本；两个 API 进程合计最多 4 个名额，并非全局队列 |
| 突发请求与数据库等待 | 每进程 64 个业务在途请求；池/连接等待默认 2 秒、锁等待 2 秒、语句 5 秒；可恢复容量错误返回 503 与 `Retry-After: 1` | 指标与健康检查豁免业务准入；每进程上限不能当成全局配额；SQL/程序错误仍是 500 |

中文搜索分词在页面事务内写入字段，数据库据此生成向量，避免“页面已保存但异步旧索引覆盖新内容”。`0003_chinese_search` 使用冻结算法回填历史数据，升级须停掉旧写入者。便携导出以一个快照读取父子关系、正文和绑定链接，导入后分配新 ID 并保留归档内部关系；不会以导出线程或 Celery 调用成功替代数据库原子性。

这些措施让系统在资源耗尽时有界等待、拒绝或恢复，并保持写入正确性；它们不保证无上限吞吐。缓存实例与 broker 分离避免缓存淘汰丢任务，仍需数据库 Outbox/滞留恢复兜底；单机、单 PostgreSQL 和单代理仍不是高可用部署。v0.4 未重新测量并发吞吐，下面保留的数字来自 **v0.2** 的短时配对实验。

## 基准方法（v0.2 历史实验）

`scripts/benchmark_concurrency.py` 使用 HTTPX 异步客户端，不依赖 Locust。每次运行经正式 API 注册全新账号、创建全新空间和 100 个固定小页面；不会登录演示账号、修改已有页面或清空 Redis。数据保留用于检查；应在独立的临时基准数据库运行，关闭对应 API 后才可删除该数据库。

默认数据是 100 页，每页初始正文 248 UTF-8 字节、一个 `[[Benchmark 0000]]` 链接，包含正式 API 创建的初始历史。不同运行仅随机账号、空间和页面 ID 不同。认证、建数据、缓存预热和历史校验不计入吞吐量。

三个场景分开报告，避免把预期冲突混入正常保存的成功率：

1. **多页面读取**：16 个请求流循环覆盖 100 页，先读取全部页面预热其版本缓存。
2. **不同页面保存**：16 个请求流各自独占一页，从版本 1 开始，连续携带上次成功返回的版本；发送不变标题与新正文。不会故意制造版本冲突。测量结束后检查每页版本号与完整、连续、无重复的历史。
3. **同一页面竞争**：另外一页进行 5 批并发提交，每批 16 个请求携带相同版本；必须正好一个 200、十五个 409，最后页面版本必须为 6，历史必须为 1–6。409 仅在此场景计为预期结果。

每个请求流最多一个在途请求，统一起跑屏障，无思考间隔。读/写场景分别持续 10 秒，截止后等待已经发出的请求完成；分母是包括排空时间的实际持续时间。延迟用 `perf_counter` 测量，P50/P95/P99 采用线性插值，包含错误请求；状态码和传输错误单独计数。它是短时闭环冒烟基准，负载产生端和服务在同一机器，不能代表开放流量、真实在线用户数、长文档、长时间稳定性、跨网络访问或生产容量。

```sh
python scripts/benchmark_concurrency.py \
  --base-url http://127.0.0.1:8012 \
  --users 16 --duration 10 --pages 100 --scenario all \
  --api-workers 2 --db-pool-size 5 --db-max-overflow 10 \
  --label after \
  --output docs/verification-artifacts/concurrency-after-100p-16u.json
```

`--api-workers` 和池参数是写入报告的人工声明，脚本不会改变或自动发现服务设置。必须先用一致配置启动两边 API。为了匹配旧代码的 SQLAlchemy 默认值，此次比较两边均用两个 API 进程、每进程 `pool_size=5 / max_overflow=10`；升级版须显式设置 `DB_POOL_SIZE=5 DB_MAX_OVERFLOW=10`。这与 Compose 的较保守默认值 `5+5` 有意区分。基准直接访问 API，未经过 Nginx，也未启动基准库的 Celery，因此不验证限速代理或后台任务负载。

## 实际证据（v0.2 历史实验）

环境为 Apple Silicon/macOS 26.6.2、Python 3.12.14、HTTPX 0.28.1、原生 PostgreSQL 17.11（55432）、Redis 7.4.7（56379）。旧版来自 `/path/to/teamwiki/backend`，使用独立的 `teamwiki_benchmark_baseline` 数据库、8011 端口、Redis DB 3。升级版使用独立的 `teamwiki_benchmark_after` 数据库、8012 端口、Redis DB 4。最终采样前，两库都重新建立并迁移为空库；两边的固定夹具、客户端连接数、进程数、池上限和请求顺序一致。

首次旧版试跑保存在 [初步基准 JSON](verification-artifacts/concurrency-baseline-preliminary-100p-16u.json)，期间另一项 Docker 构建可能争用 CPU，且保存请求只发送正文；因此只用来验证脚本和旧版一致性，不用于改进比例。该次所有普通请求成功，5 批热点竞争均为一胜十五冲突，历史连续。试跑数据随后随基准库重建清理。

最终对照在 Docker 构建与主动栈验证结束后顺序执行：旧版报告时间为 `2026-10-26T04:47:11Z`，升级版为 `04:47:39Z`。容器保持空闲，仍有轻量定时健康检查及 Beat 活动。升级版启用实际运行时指标与边界保护。原始结果为 [旧版 JSON](verification-artifacts/concurrency-baseline-100p-16u.json) 与 [升级版 JSON](verification-artifacts/concurrency-after-100p-16u.json)。

| 场景 | 版本 | 请求数/状态 | 实际秒数 | 请求/秒 | P50 ms | P95 ms | P99 ms |
| --- | --- | --- | ---: | ---: | ---: | ---: | ---: |
| 多页面读取 | 旧版 | 7401 × 200 | 10.0163 | 738.892 | 9.322 | 73.630 | 122.115 |
| 多页面读取 | 升级版 | 7545 × 200 | 10.0105 | 753.711 | 8.964 | 70.733 | 114.962 |
| 不同页面保存 | 旧版 | 1380 × 200 | 10.1180 | 136.390 | 114.217 | 138.778 | 163.614 |
| 不同页面保存 | 升级版 | 7658 × 200 | 10.0112 | 764.940 | 19.550 | 32.144 | 45.791 |
| 热点版本竞争 | 旧版 | 5 × 200，75 × 409 | 0.1813 | 441.321 | 22.837 | 31.960 | 37.169 |
| 热点版本竞争 | 升级版 | 5 × 200，75 × 409 | 0.1574 | 508.392 | 20.811 | 28.424 | 30.770 |

此单次配对冒烟中，读取指标接近；不同页面保存吞吐为旧版的 5.61 倍，P95 从 138.778 ms 降至 32.144 ms。该比较包含共享锁、来源页链接索引、连接复用和运行时指标等全部改动，不能单独归因于某一个改动。所有普通请求均为 200、无传输错误；16 页累计验证的完整历史分别为 1396 条和 7674 条（含每页初始版本）。两边热点页面都正好 5 次提交成功，最后版本为 6、历史为 1–6。热点的“请求/秒”包含预期冲突响应，不代表同一页每秒能接受该数量的修改。

对应原生升级版启动参数如下，迁移须在同一数据库 URL 下先执行 `alembic upgrade head`；旧版进程使用其原始目录和独立旧版数据库，SQLAlchemy 池的默认值即为 `5+10`。

```sh
DATABASE_URL=postgresql+asyncpg://teamwiki:teamwiki@127.0.0.1:55432/teamwiki_benchmark_after \
REDIS_URL=redis://127.0.0.1:56379/4 \
DB_POOL_SIZE=5 DB_MAX_OVERFLOW=10 \
PYTHONPATH="$PWD/backend" \
python -m uvicorn app.main:app --host 127.0.0.1 --port 8012 --workers 2 --no-access-log
```

目前的结果不构成线上 SLA。正式上线前应在目标机器重复多轮、以中位数及波动范围比较；覆盖更大的空间、长正文、搜索/图谱/导入混合负载，并同步观察数据库连接等待、锁等待、CPU、内存、缓存命中与错误率。一次短测的吞吐量不能外推为“支持 N 人同时编辑”。

## 其他检查

```sh
python -m unittest discover -s backend/tests -p test_benchmark.py -v
ruff check scripts/benchmark_concurrency.py scripts/locustfile.py backend/tests/test_benchmark.py
```

三个轻量测试验证百分位、空结果、错误率计算，以及热点必须正好一个成功的判定，不接触应用测试数据库。完整业务测试由应用测试流程单独执行。

`scripts/locustfile.py` 保留用于探索性混合负载，必须显式设置 `LOAD_EMAIL`、`LOAD_PASSWORD`、`LOAD_WORKSPACE_ID`，每个虚拟用户只写自己的新测试页；不会默认选择演示空间。其请求比例和思考间隔与上述基准不同，结果不能放在同一张前后对比表中。
